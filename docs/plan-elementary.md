## 0. 承認が必要なもの（先に明記）

| 項目 | いつ | 理由 |
|---|---|---|
| Web 公開（ホスティング。GitHub Pages・Firebase Hosting など） | 第2段階の前、またはテスト版を家族以外に見せるとき | 外部公開。Google ログインは `file://` では動かず、**公開された URL（承認済みドメイン）が必須** |
| Firebase（または Google Cloud）プロジェクトの作成、Google ログインの設定、API キー／クライアント ID の発行 | 第2段階 | 外部サービスの契約・設定。無料枠（Spark プラン等）で足りる想定だが、**料金・無料枠の条件は着手時に公式で確認**し、課金が発生しうる設定（Blaze への切替、請求先の登録）は行わない。キーを発行する前に承認を取る |
| プライバシーポリシー／保護者向け説明の公開 | 第2段階の公開前 | 個人情報（ログイン情報）を扱うため。文面は企画部が下書きし、公開は承認事項 |
| 英語の「端末外の声」を許すか（前からの U6） | 第2段階と同時 | 通信が発生するため（7章） |

- 第1段階（端末内保存、プロフィール、レベルの階段）は**承認不要**で、これまでと同じくローカルで遊べる状態まで出せる。
- 有料サービスは使わない前提。本企画に課金は含まれない。
- なお、現在のテスト版は claude.ai の非公開 Artifact（メモリより）。その環境で Google ログインが動くかは**未確認**（動かない可能性が高いと見ている）。ログインの試験は、承認後に用意する別のホスティングで行う前提にする。

## 1. 目的・対象ユーザー・範囲・完了条件

### 目的
- 就学前（4〜6歳）向けに作ってきた「はたらく車で学ぶ」アプリを、**小学校低学年（小1〜小2）の学習の入門**まで、順に進める1本の階段として続けられるようにする。
- 同じタブレットを兄弟で使っても、それぞれの**レベルと進み具合が混ざらず、次回は続きから**始められるようにする。
- 保護者の Google アカウントでログインすると、**進み具合が保存され、別の端末でも引き継げる**ようにする（ただし端末内保存を先に出す。4章）。

### 対象ユーザー
- 主: 4歳〜小学2年生くらい（未就学 → 小1 → 小2）。小学生は字が読める前提のレベルが増える。未就学のレベルは従来どおり字が読めなくても遊べる。
- 副: 保護者。子どものプロフィール管理、ログイン、進み具合の確認、データ消去。
- 同じタブレットを使う兄弟（2〜4人を想定。上限は U6）。

### 守る原則（plan.md 1章）を小2まで維持するか
| 原則 | 方針 |
|---|---|
| 失敗状態なし（1回目の誤答で無効化、2回目でヒント、必ず正解して進む） | **維持**。点数・減点・タイマー切れは入れない |
| 1回4問（約2〜3分） | **維持**（定数 `QUESTIONS_PER_SESSION`）。小学生で長すぎ・短すぎなら調整（U12） |
| 声が出なくても進める | 未就学のレベルは従来どおり。**小学生のレベルは文字で読めるので、声なしでも進める度合いが上がる**（むしろ有利）。ただし えいご は従来どおり声が必要 |
| 画面の文字はひらがなのみ（UI） | **要改訂**。小学生は漢字を習うので、一律ひらがなは幼く見える。方針は 2.5 と U4 |
| 通信ゼロ・個人情報なし | 第1段階は**維持**。第2段階（ログイン）で崩れる。明記して保護者に説明する（5章） |

### やること
1. レベルの階段（未就学 → 小1 → 小2）と解放条件の導入（2章）。既存の4ゲーム（かず・もじ・とけい・えいご）を階段に配置し、小1・小2の新しいレベルを追加する。
2. 子どもプロフィール（ニックネーム＋アイコン）と、同じタブレットでの切り替え（3章）。
3. 端末内保存（第1段階）と、Google ログインでの保存・別端末での引き継ぎ（第2段階）（4章）。
4. 子どもの情報の最小化、保護者向けの説明、データ消去（5章）。
5. 段階ごとのリリース計画（8章）。

### やらないこと（今回）
- 小3以上の内容、教科書の網羅（「入門」を超える範囲）。成績評価・テスト・順位づけ・ランキング・他人との比較。
- 学校との連携、先生用画面、保護者への自動メール通知、広告、課金、SNS 共有。
- 子ども自身の Google アカウントでのログイン（ファミリーリンクが必要。3.3 の代案としてのみ検討）。
- 手書き認識（漢字の書き取り・筆順判定）。選択式を基本とする。
- 本書では**技術の細部（データ構造・コード）は決めない**。設計部が後で行う。
- ネイティブアプリ化（App Store／Google Play）。

### 完了条件（本企画全体）
8章の各段階の完了条件を満たし、純粋関数のテストが通り、reviewer のレビューを経て main に PR 経由でマージされていること。第2段階は、承認を得て外部サービスを設定したうえで、実際のログイン・保存・別端末での復元を動作確認できること。

## 2. レベルの階段

### 2.1 「小学生向け」を別モードにするか、延長して1本の階段にするか（最も設計に効く判断）

| 案 | 内容 | 良い点 | 難点 |
|---|---|---|---|
| **A. 1本の階段（推奨）** | 今の4ゲームの上に、ステージ（未就学 → 小1 → 小2）を積む。ゲームごとのレベル（M・K・T・E）は今のまま延長し、ステージはそれらの「まとまり」と「解放の関門」になる | 既存の保存・昇降級・保護者画面・テスト・出動えらびをほぼそのまま使える。「順に進む」という依頼にそのまま合う。兄弟で年齢差があっても、同じアプリで各自のステージに進める。弟が兄のステージを覗くこともできる | 画面の文字方針（ひらがなのみ）や出題の難しさが同じアプリの中で混在する。UI の見た目を小学生向けに寄せる工夫が必要（2.5） |
| B. 別モード（「しょうがくせい」モードを別に作る） | タイトルで「みしゅうがく／しょうがくせい」を選ぶ。小学生向けは独立した画面・出題・保存 | 見た目も文字方針も小学生向けに割り切れる。幼い見た目を嫌がる小学生に合う | 作る量が倍に近い（出動えらび・保護者画面・保存・テストが二系統）。「順に進む」ではなく「切り替える」になり、依頼とずれる。兄弟の年齢差に対し、モード選択をまたぐ進捗管理が複雑 |
| C. 別アプリ（別の案件として作る） | 小学生版を別リポジトリで作る | 完全に分離でき、未就学版を壊さない | 重複が最大。共通部分（絵・音・出動の流れ）の二重管理。ログイン・保存も二重に |

**推奨: A（1本の階段）**。理由: 依頼の本文が「順に進む」「レベル保持」「次回から続き」で、同じ仕組みの延長で実現できる。実装コストが最も小さく、既存の資産（4ゲーム、自動昇降級、31語の単語表、ごほうび）をそのまま活かせる。B の長所（小学生の見た目）は、A の中で「ステージごとの見た目の切り替え」（2.5）で一部取り込める。C は採らない。

**この判断の見直し条件**: 小2のテスト遊びで「見た目が幼くて嫌がる」が強く出たら、小2ステージだけ見た目を大きく変える（B に寄せる）。階段の構造は変えずに済むようにしておく。

|---|---|---|---|
| S0 | みならい しょうぼうし | みしゅうがく | M1〜M5、K1〜K6、T1〜T3、E1〜E3 |
| S1 | しょうぼうし | 小学1年生くらい | 既存の M6・M7（ひきざん）、T4〜T6（15分・5分刻み・経過時間）＋新規。下表 |
| S2 | たいいん | 小学2年生くらい | 新規。下表 |

- 新規レベルは**1ゲームにつき数段**に抑える（小2まで合計で、かず+6、もじ+3、とけい+2、えいご+2 程度。作る量の見積もりは設計部）。

### 2.3 解放条件（何をクリアしたら次が開くか）

**推奨: 「ステージの関門」＋「ゲーム内の自動昇降級」の二段構え。**

1. **ゲーム内**（既存どおり）: 直近の出動で1回目正解が 4/4 なら次のレベル、0〜1/4 なら前のレベル。固定も可。**この自動昇降級は、解放済みのステージの中だけで働く**（未解放のステージのレベルには自動では上がらない。ステージの最終レベルで 4/4 になっても、次のステージは開かない）。
2. **ステージの関門**: 次のステージは、**かず・もじ・とけいの3ゲームすべてで、そのステージの最終レベルを 4/4（1回目正解）で1回クリア**したときに開く。えいごは関門に含めない（英語の声のない端末があるため。また、小学校の中心教科ではないため）。
   - S0 → S1 の関門: M5・K6・T3 を各1回 4/4。
   - S1 → S2 の関門: M10・K8・T6 を各1回 4/4（レベル ID は仮）。
   - 理由: 1ゲームだけ得意でも先に進めてしまうと、他が置き去りになる。逆に、苦手なゲームが関門になって行き詰まらないよう、**保護者は保護者画面から手動でステージを解放／再ロックできる**（不安なら戻せる）。
3. **解放の見せ方**: 関門を満たした出動の後に、「しょうぼうし に しょうかく！」のような昇格の演出（ヘルメットやワッペンを授与。特別なごほうび、2.5）を入れる。次のステージには、**子どもが自分で「すすむ」を選ぶ**（勝手に切り替わらない。切り替えを保護者がやってもよい）。
4. **記録**: ステージの修了は、日付つきで保存する（プロフィールごと。4章）。

**代案**
- ゲームごとに独立して進める（関門なし）: 単純だが、「順に進む」という依頼の趣旨（学びの順序）が弱くなる。
- テスト形式の関門（「しゅっぱつ しけん」として、各ゲーム4問を続けて）: 到達確認が明確だが、「失敗状態なし」の原則とぶつかりやすい。採らない。
- 保護者の手動解放のみ: 保護者の手間が大きい。補助としてのみ残す。

### 2.4 前のレベルに戻って遊べるか
- **戻れる（常に自由）**。ステージ選択（出動えらびの上、または前の画面）で、解放済みのステージを選べる。兄姉の隣で弟が S0 を遊ぶ、小学生が S0 の復習をする、のどちらも自然にできる。
- 戻って遊んでも、**その子の進み具合（現在のレベル・関門の記録）は進まない／戻らない**（別枠扱い）。ただしごほうび（カード）は、どのステージで遊んでももらえる（2.5）。
- 保護者画面で、ゲームごとの現在のレベル固定は従来どおり。

### 2.5 世界観の保ち方（働く車の世界を小学生向けにどう保つか）
- **階級制にする**: みならい → しょうぼうし → たいいん（隊員）。学年名は子どもに出さず、階級で呼ぶ。「大きくなった」実感が出る。
- **ステージごとに消防署の見た目を成長させる**: S1 で署の看板・制服・ヘルメットの色が変わる、S2 で「きゅうじょたい」（救助隊）の車が加わる、など。小学生は「幼稚っぽい」を嫌うため、**タイトル・出動えらび・現場の配色と文言のトーンを少し落ち着かせる**（点滅や過剰な擬音を減らす。2.1 の見直し条件に対応）。
- **ごほうび**: 既存のカード（11種×★3）は全ステージ共通で集められる。S1・S2 では、**上位の働く車**（例: 救助工作車、化学消防車、はしごの大型車など。実在メーカーのロゴは使わない）を新カードに足す案（plan-katakana-english.md 2.10 の「しゃこ拡張 PR-B4」の働く車6種と合流させてよい）。S1・S2 昇格時には、特別なワッペン（階級章）をもらう。
- **現場の話を学年に合わせる**: 現場の3種（かじ・たかいところ・みちのこまりごと）は共通。小学生向けの問題では、題材を「時刻の出動表」「現場までの道のり（ひきざん）」「資材の個数（かけざん）」のように現場の話につなげる（問題の文は読める子向けに短い文章で出す）。
- **UI の文字**: 現行の「UI 文言はひらがなのみ」は、**S0 のみ厳守**。S1 以降は、**そのステージまでに習う漢字（教材として出した漢字）に限り UI に使ってよい**案を推奨（読みはふりがな付き）。迷う点なので U4 に挙げる。代案は「UI は全ステージひらがなのまま（漢字は教材にだけ出す）」で、実装は軽く、既存の受け入れ条件（子ども向け画面はひらがなのみ）を変えずに済む。
- **保つもの**: 失敗状態なし、1回4問、ごほうび、現場の演出、実在ロゴなし、外部画像なし、通信ゼロ（第1段階）。

## 3. 子どもプロフィールと同一タブレット

### 3.1 前提
- 現在の保存は `hataraku-manabi:v1` の1つの JSON（1人分）。ごほうびカード、レベル、統計、音の設定がすべてその中にある。**「複数の子ども」は plan.md で MVP 外**だった（今回の拡張で必要になる）。
- 同じタブレットを兄弟で使う。兄弟は年齢が違う（未就学と小学生）ことが多く、レベルが違うのが普通。

### 3.2 プロフィールの仕様（企画の範囲）
- **名前（ニックネーム）とアイコン**のみ。本名は求めない（5章）。アイコンははたらく車のイラストから選ぶ（12種程度。写真は使わない）。名前は**ひらがなで最大6文字程度**（子どもが読み書きできる範囲。未就学の子は、保護者が入力する）。
- 子ども用の入力は、**画面上のひらがなパネルを自前で用意する**（端末のキーボードを出さない案。誤入力と外部変換候補を避ける）。ただし作りは設計部に任せる。
- **人数は端末あたり最大4人**（暫定。U6）。
- プロフィールごとに持つもの: レベル（ゲームごと）、ステージの解放状態、統計、ごほうびカード（★含む）、直近に出した問題の履歴（偏り防止）。
- **端末共通で持つもの**: 音のオン/オフ（保護者設定）、読み上げテストの結果など端末依存のもの。
- **ごほうびカードをプロフィール別にするか、共有にするか**: 推奨は**別々**（兄弟でカードを取り合わない、自分のしゃこを持てる）。ただし「兄弟で一緒に集める」遊び方もあり得るため U5 に残す。
- **切り替え**: アプリを開くと「だれが あそぶ？」でアイコンを選ぶ（直前に使った子を先頭にする）。遊んでいる途中の切り替えは、タイトルに戻ってから。誤って別の子の記録を進めないよう、**タイトル画面に今のプロフィール名とアイコンを常に表示**する。子どもによるプロフィール選択は、PIN などを付けず自由（兄弟が覗き合うのは許容）。
- **プロフィールの追加・名前の変更・削除は保護者画面で行う**（既存の「長押し2秒」の保護者画面）。削除は2段階の確認（既存のデータ消去と同じ流れ）。

### 3.3 ログインとプロフィールの関係（13歳未満への配慮）
13歳未満の子どもが**自分の Google アカウント**を持つには、保護者のファミリーリンクでの管理が必要になる。小学生の子どもに自分のアカウントを作ってログインさせるのは、保護者の負担と同意の手間が大きく、同じタブレットで兄弟が切り替えるのにも向かない。

| 案 | 内容 | 判断 |
|---|---|---|
| **A. 保護者の Google アカウントでログイン＋その中に子どもプロフィール（推奨）** | ログインするのは保護者。1つのアカウントの中に、子どもプロフィール（最大4人）が入る。子どもはログインの操作をしない | 13歳未満の子ども自身が Google に登録する必要がない。兄弟が同じタブレットで切り替えられる。保護者の1アカウントで全員の記録が別端末に引き継がれる。子どものデータはニックネームと進み具合だけで済む |
| B. 子どもごとに Google アカウント（ファミリーリンク） | 子ども1人ごとにアカウントでログイン | 子どもの識別は明確だが、兄弟ごとにログイン切替が必要。ファミリーリンクの設定は保護者の負担。同じタブレットで切り替えにくい。採らない |
| C. ログインなし（端末内保存のみ） | 第1段階で止める | 最も安全で簡単だが、依頼の「Google アカウントでのログインでレベル保持」を満たさない。第1段階として残す |
| D. 1アカウント＝1人（プロフィールなし） | 兄弟は別アカウントを使い分ける | 同じタブレットでの切り替えが難しく、依頼の「同一タブレット」と合わない。採らない |

**推奨: A**。ログインは保護者画面からのみ行い、子ども向け画面にはログイン操作を出さない（誤操作・誤入力を防ぐ）。

## 4. 保存の段階分け

### 4.1 第1段階: 端末内保存（承認不要・すぐ出せる）
- 保存先は今と同じブラウザの `localStorage`。**通信ゼロ・個人情報の外部送信なしのまま**、同じタブレットで次回は続きから遊べる。
- プロフィールごとに、レベル・ステージ・統計・ごほうびを保存する。保存データのバージョンは **v1 → v2 に上げる**（設計部が決める）。
- **既存データの引き継ぎ**: 既に v1 のデータがある端末（例: 現在遊んでいる子）は、起動時に**最初のプロフィール**として自動で取り込む（レベル・カード・統計を失わない）。名前は仮に「こども1」とし、保護者画面で変更できる。移行は一度だけ、元の v1 は一定期間（次の版まで）残す。
- 注意すべき制約（保護者画面で案内）: ブラウザのデータを消すと記録も消える／プライベートブラウズでは保存できない（従来どおり、メモリのみで動く）／**端末を変える、別のブラウザで開くと引き継がれない**（第2段階で解決）。
- **iOS Safari の注意**: ホーム画面に追加しない通常のブラウザでは、長期間（約7日）使わないと保存が消されることがある（ブラウザの仕様。詳細は設計部が調査）。保護者画面に「保存が消える場合がある」旨の注意と、第2段階への案内を出す。

### 4.2 第2段階: Google ログインでの保存・別端末での引き継ぎ（承認が必要）
- **候補A: Firebase Authentication（Google ログイン）＋ Cloud Firestore**。保護者のアカウントごとに、プロフィールと進み具合を保存する。無料枠（Spark プラン等）で足りる見込みだが、**料金・無料枠の条件は着手時に公式を確認し、承認を取る**。
- **候補B: Google ログイン＋ Google ドライブの「アプリ専用データ」領域に保存**。保存先が保護者自身の Google ドライブで、**運営側のサーバーに子どものデータを持たない**（5章の方針と相性が良い）。サーバー側の設定が少なく済む可能性があるが、Google Cloud でのクライアント ID の発行と同意画面の設定が要る。通信の失敗・同期の衝突の扱いは候補A と同様に必要。
- **候補C: 自前サーバー**。運用負荷と責任が大きいため採らない。
- 推奨は**候補A**（情報が多く、実装例が豊富）。ただし、**子どもの情報を運営側に預からない設計（候補B）の方が説明がしやすい**という見方もあるため、どちらにするかは設計部の比較（技術調査）の後、ユーザーに確認する（U9）。
- **外部サービスの設定・キー（API キー／クライアント ID）の発行は人間の承認が必要**。企画部・設計部は準備（手順書の下書き）までにとどめる。
- **ホスティングが必須**: Google ログインは `file://` では動かない。公開された URL（またはローカルサーバー）が要る。現行の「`file://` で開いて遊べる」は、**ログインなしの動作として残す**（ログインが使えない状況でも、第1段階の機能でそのまま遊べる）。公開先（GitHub Pages・Firebase Hosting など）は承認事項（U10）。
- **ビルドなしの方針との整合**: 現行は外部 CDN・外部ライブラリなし、classic script。Firebase の SDK は通常モジュール形式で配布され、CDN からの読み込みが一般的。**SDK をリポジトリに同梱するか、CDN を許すか、ビルド工程を入れるか**は設計の判断（U11）。第1段階には影響しない。
- **ログインの出し方**: 保護者画面の中だけ。子ども向け画面には出さない。ログイン前でも従来どおり遊べる。ログインしていない間は、第1段階（端末内保存）で動く。
- **オフライン時**: 端末内に保存し、通信が戻ったら同期する（同期が失敗しても遊びを止めない。失敗状態なしの原則）。

### 4.3 端末内の記録のログイン後の引き継ぎ（方針）
1. 初めてログインしたとき、端末内のプロフィールを一覧で示し、**「このアカウントに保存する？」と保護者が選ぶ**（勝手にアップロードしない）。
2. クラウド側に既にデータがある（別の端末で保存済み）場合は、マージする。**規則の案**: プロフィールは名前＋アイコンでなくプロフィール ID で対応づけ、同じプロフィールの記録は「レベルは高い方、ごほうびの★は大きい方、ステージの修了は和集合、統計は大きい方」を採る（二重加算を避ける）。衝突しそうなときは、保護者に「この端末の記録／アカウントの記録」を選ばせる。細かい規則は設計部が決め、ユーザーに確認する（U13）。
3. ログアウトしても、端末内の記録は残す（共有タブレットの引き継ぎミスを防ぐため、ログアウト時に「この端末の記録を消す？」を選ばせる）。
4. 家族以外の端末でログインした場合は、保護者画面から「この端末の記録を消す」を用意する。

## 5. 子どもの個人情報の扱い

### 5.1 方針
- **保存する情報は最小限**: ニックネーム（ひらがな。本名を入れないよう案内）、アイコン、レベル・ステージ・統計・ごほうび。**生年月日・学年・写真・位置情報・連絡先は保存しない**。学年の目安は、レベルの進み具合から表示するだけで、入力させない。
- ログイン情報（メールアドレスなど）は**保護者のもの**。Google が管理し、アプリは識別のための ID を使う。子どもの Google アカウントは使わない。
- **広告・行動分析・第三者提供・外部トラッキングは行わない**。クラッシュ報告などの外部送信も、入れる場合は事前に承認を取る。
- 第1段階は、従来どおり**外部送信なし**。第2段階で初めて、保護者がログインして保存を選んだデータだけが、選んだ保存先（Firebase 等）に送られる。
- **削除できる**: 保護者画面から、プロフィール単位・アカウント全体の削除ができる（クラウドのデータも消える。消去が完了するまでの時間・バックアップの扱いは設計部が確認）。

### 5.2 保護者向けの説明（作る文面の要点）
保護者画面（ログインの前）に、短い説明を出す。公開時はプライバシーポリシーとして独立ページにする（企画部が下書き、公開は承認事項）。
- 保存する情報と目的（上記のみ、遊びの続きと別端末での引き継ぎのため）。
- 保存する場所（第1段階: この端末のブラウザの中だけ／第2段階: 選んだ保存先。通信が発生すること）。
- 子どもの個人情報は広告や第三者に使わない／売らない。
- 削除の方法。
- ニックネームには本名・学校名などを入れないでほしいという案内。
- 13歳未満の子どもはログインせず、保護者がログインして使うこと。
- 英語の読み上げについて（端末外の声を許す場合のみ）: 読み上げのため、英単語の文字列が端末の外に送られることがある（7章 U6）。

> 日本の個人情報保護法、および公開時に適用されうる各国の子ども向けオンラインサービスの規制（米国の COPPA など）、Google のサービス利用規約の「子ども向け」条項に適合させる必要があるかは、**企画部では判断できない**。公開前に、ユーザー（または専門家）の確認を取る（U14）。これは法的助言ではない。

### R3: 小2ステージ（承認不要）

- **完了条件**: R2 の完了条件 1〜6 の S2 版。九九の問題の全数テスト（答え・選択肢の性質）。小2の遊び心地の確認（ユーザーまたは実際の子どもによる試遊。結果は記録するが、効果の評価はしない）。

### R4: 第2段階 — Google ログインでの保存・別端末での引き継ぎ（**承認が必要**）
- 事前（準備のみ。企画部・設計部）: 候補A／Bの技術比較、手順書、保護者向けの説明文・プライバシーポリシーの下書き、費用の見込み。
- **承認を得てから**: ホスティングの決定、Firebase（または Google Cloud）プロジェクトの作成、ログイン設定、キー／クライアント ID の発行（人間が行うか、承認のうえ実施）。
- 実装: 保護者画面からのログイン、プロフィールのクラウド保存と取得、端末内記録の引き継ぎ（4.3）、ログアウト・データ削除、同期失敗時の動作。
- R3 より先に行ってもよい（R1 の後ならいつでも着手可能。承認とホスティングの確定が揃った順）。
- **完了条件**
  1. 実際の Google アカウント（保護者）でログインでき、端末Aで進めた記録が端末Bで復元される（実機で確認）。
  2. 端末内の記録がログイン後に引き継がれ、既存のクラウドデータとの衝突時に保護者が選べる。記録が失われない。
  3. ログイン前・ログイン不可の環境でも、従来どおり遊べる（第1段階の動作が壊れない）。同期失敗で遊びが止まらない。
  4. 子ども向け画面にログイン操作が出ない。保存されるのは 5.1 の最小限の情報だけ。プロフィール単位・アカウント全体の削除ができる。
  5. 保護者向けの説明（通信が発生すること、保存先、削除方法）が表示される。
  6. 無料枠の範囲内で動くこと、課金が発生する設定になっていないこと（承認者が確認）。
  7. U6（端末外の英語の声）が決定し、説明に反映されている。
  8. 公開（Web 公開）は、別途承認を得て実施されている。

### 順序の理由
R1 を最初にするのは、保存の構造変更（v2）が全体に効き、その上に階段（R2・R3）とログイン（R4）が載るため。R1 だけで「同一タブレットで続きから」が実現し、承認も不要で、依頼の一部がすぐ届く。小学生向けの中身（R2・R3）とログイン（R4）は互いに独立なので、承認待ちの間も R2・R3 を進められる。
