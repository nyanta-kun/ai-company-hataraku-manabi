  "device": {
    "sound": { "sfx": true, "voice": true },
    "lastProfileId": "p_lq3k9x_7f2a",
    "migratedV1": "2026-10-25"

      "id": "p_lq3k9x_7f2a",

| 〃 | `levels, locked, cards, stats, seen, lastPlayed` | **v1 と同じ形・同じ意味**（`src/storage.js:10-27` から `version`・`sound` を抜いたもの） |

- 読み上げテストの結果・声なしモードは保存していない（`src/speech.js` の実行時の状態）。今回も保存しない。
- **プロフィールの中身を v1 と同じ形にする理由**: (1) 既存の `normalize`（`src/storage.js:32-53`）を `normalizeProfile` として、ほぼそのまま使える。既存の `tests/storage.test.js` の 8 本も、関数名を差し替えるだけで生き残る。(2) ui.js は「`data` を今のプロフィールに向ける」だけで、`data.levels` などの参照（1章の表）を書き換えずに済む。

### 2.2 読み込みの順番と v1→v2 の移行

`load()` は次の順で決める（**v2 があれば v1 は見ない**）。

1. `localStorage` が使えない（取得・`getItem` で例外） → `persistent=false`。メモリ上の既定（こども1 が 1 人）で動く。
2. v2 キーがあり、`JSON.parse` できる → `normalize(raw)`。
3. v2 キーがあるが `JSON.parse` できない（壊れた文字列） → 壊れた文字列を `hataraku-manabi:v2:broken` に 1 つだけ退避（上書き）し、4 へ進む。
   - JSON として読めても object でない、または有効な id のプロフィールが 0 人の場合も、壊れた扱い（3）にする。
4. v1 キーがあり、`JSON.parse` できる → `migrateV1(raw, id, today)` で取り込み、**すぐ v2 に保存**する。v1 キーは消さない。
5. どれでもない（新しい端末、または v1 も壊れている） → 既定（こども1 が 1 人）。保存は最初の `save()` のとき。

`migrateV1(rawV1, id, today)`（純粋関数）:
- `profile = normalizeProfile(rawV1)` に `id`、`name: 'こども1'`、`icon: 'shoubousha'`、`created: today` を足す。
- `device.sound` は `rawV1.sound` から（`bool` で補正。v1 の `normalize` と同じ規則）。
- `device.migratedV1 = today`、`device.lastProfileId = id`。
- U3 の回答により、今あるレベルはすべて S0。**移行でレベル・カード・統計・直近の絵は変えない**（S1 の自動解放もしない。企画 9章 U3・U15）。

v1 キーの扱い:
- 残す（企画 4.1「元の v1 は一定期間（次の版まで）残す」）。v2 ができた後は読まないので、v1 は移行した日の状態のまま止まる。
- **「データをけす」（全消去）は v1 も消す**。v2 だけ消すと、次の起動で手順 4 が v1 を再び取り込み、消したはずの記録が戻ってしまうため。
- v1 キーを消す時期: R2 のマージ後、次の版（R3）で `load` の中で消す、を案とする（企画の「次の版まで」）。それまでは残す。

v2 が壊れていて v1 から取り込み直した場合、v1 は移行した日の古い記録なので、それ以後の進み具合は失われる。何も無いよりは良いので取り込むが、保護者画面の「データ」カードに「ほぞんデータが こわれていたので、まえの きろくから もどしました」を 1 回だけ出す（`device.restoredFromV1` を立て、表示したら消す）。

### 2.3 保存・メモリのみ・複数タブ

- `save(state)`: v2 キーに丸ごと書く。失敗（容量・プライベートブラウズ・権限）なら `persistent=false`。今と同じく例外は外に出さない（`src/storage.js:67-74`）。
- メモリのみのときも、プロフィールの追加・切り替えは動く（閉じると消える）。保護者画面の `p-storage-note`（`index.html:109`）を出す。今の文言のまま。
- 複数のタブで同時に開くと後から保存した方が勝つ（今と同じ）。`storage` イベントでの同期はしない（子どもの使い方で起きにくく、作る量に見合わない）。
- 書き込む量の目安: 1 人あたり 1KB 前後、4 人で数 KB。容量の心配はない。

**推奨: A**。理由: 企画 3.2 で自前パネルを挙げたのは「子どもが入力する」場合の誤入力と変換候補を避けるためだったが、ユーザー回答で名前の入力は保護者画面で保護者が行うことになり、その理由が薄れた。A は実装・テストとも小さく、iPhone の小さい画面でも端末の標準の入力になる。B は「子どもが自分で名前を変えたい」要望が出たときの拡張として残す（そのときは 2 段階方式。寸法は下の付記）。

#### A の作り

- 保護者画面の「こども」カード（2.7）で「なまえ」を押すと、そのカードの中に入力欄 + 「きめる」「やめる」を出す（別画面やダイアログにしない。`prompt()` も使わない）。
- `<input type="text" maxlength="12" autocomplete="off" autocapitalize="off" spellcheck="false" enterkeyhint="done">`。**`font-size` は 16px 以上**（iOS Safari は 16px 未満の入力欄にフォーカスすると画面を拡大する）。
- iPhone ではキーボードが下半分を覆うので、入力欄はカードの上部に出し、出したときに `scrollIntoView({ block: 'center' })` する。
- 「きめる」で `normalizeName(value)`:
  1. 前後の空白を除く。
  2. カタカナはひらがなに直す（`D.toHira`、`src/data.js:50-52`）。
  3. 残す文字は ひらがな（`ぁ`〜`ゖ`）と長音 `ー` だけ。それ以外が 1 文字でもあれば**直さずに**「ひらがなで いれてね」と出して保存しない（漢字やローマ字を黙って消すと、意図しない名前になるため）。
  4. 6 文字を超えたら「6もじ までに してね」。
  5. 空なら「なまえを いれてね」。
- IME の変換中（`compositionstart`〜`compositionend`）は検査しない。検査は「きめる」のときだけ。
- 本名を入れないでほしい旨を入力欄の下に小さく出す（企画 5.1・5.2）。「ほんみょうでは なく、よびなを いれてください」。

`normalizeName` の戻り値の形: `{ ok: true, name }` または `{ ok: false, reason: 'empty'|'chars'|'long' }`。`addProfile` / `renameProfile` は内部でこれを使う。

付記（B を採る場合の寸法）: 1 段目に行（あ か さ た な は ま や ら わ）を 5 列×2 段（iPhone 縦で 1 キー約 64×52px）、行を押すと 2 段目にその行の 5 文字と「゛」「゜」「小」「ー」「けす」を出す。

### 2.7 保護者画面の変更

カード「こども」を一番上に足す。

### 2.8 iPad / iPhone（Safari）での保存の注意

確かめた事実（出典は 9 章）:

1. **Safari で開いている場合**: WebKit の追跡防止（ITP）は、スクリプトで書く保存（localStorage・IndexedDB など）を「Safari を使った 7 日間、そのサイトを操作しなかった」ときに消す。ホーム画面に追加したウェブアプリは Safari とは別に日数を数え、そのアプリを使った日だけ進むので、実質的に消えにくい（WebKit 公式ブログ）。ただしホーム画面のアプリでも 7 日で消えたという報告がバグ管理に残っており（WebKit Bugzilla 237350）、確実とは言えない。
2. **ホーム画面に追加したアプリと Safari は保存領域が別**（WebKit Bugzilla 181849。WebKit の開発者が「意図した動き」と回答）。Safari で遊んだ記録は、後からホーム画面に追加したアプリには引き継がれない（逆も同じ）。
3. 端末を変える・別のブラウザで開く・Safari の「履歴とWebサイトデータを消去」で記録は消える（企画 4.1）。プライベートブラウズでは閉じると消える。

保護者画面の文言（「データ」カード。ひらがな中心。保護者向けなので句読点を多めに）:

> きろくは この たんまつの ブラウザの なかだけに ほぞんします（そとには おくりません）。
> ・iPad / iPhone の Safari で ひらいて いる ときは、7にちくらい あそばないと きろくが きえる ことが あります。**さきに「ホームがめんに ついか」してから** あそぶと きえにくく なります。
> ・Safari で あそんだ きろくは、あとから ホームがめんに ついかした ほうには ひきつがれません（べつの ほぞんばしょ に なります）。
> ・たんまつを かえたり、ブラウザの データを けしたり すると きろくは きえます。

- 「ホーム画面に追加してから遊ぶ」を先に案内するのは 2. のため。すでに Safari で遊んでいる家庭が後から追加すると、記録が空に見える。R1 では Safari 側の記録をホーム画面側へ移す手段を作らない（R4 のログインで解決する）。このことも文言に入れた。
- **前提の確認（ブロッカー候補）**: 今のテスト版は claude.ai の非公開 Artifact（`docs/plan-elementary.md:23`）。Artifact の中（サンドボックスの iframe）では `localStorage` そのものが使えない可能性がある。その場合 R1 はメモリのみで動き、完了条件 1（リロード後も続き）を満たせない。`file://` で開けない iPad/iPhone で保存を確かめるには、何らかの配信元（ホスティング）が要る。2.9 の手順の最初でこれを確かめ、保存できなければ「ホスティングの判断（承認事項）を R1 に前倒しする」かをユーザーに聞く。

### 3.3 出題レベルと昇降級の規則（純粋関数で決める）

子どもがステージ s（`stage.current`）でゲーム g を選んだときの規則。`lv = levels[g]`、`range = s の levels[g]`（えいごは 3.1 の読み替え）。

| 場合 | 出題するレベル | 終わった後 |
|---|---|---|
| `lv` が s の中 | `lv` | `nextLevel` で更新。**上下とも s の範囲で止める**（下のステージへは自動で落ちない。上の未解放ステージへも上がらない） |
| `lv` が s より下（S1 に進んだばかり。保護者の手動解放の直後など） | s の最初のレベル | `nextLevel` で更新（s の範囲） |
| `lv` が s より上（S1 の子が S0 で遊ぶ＝復習） | s の最後のレベル（S0 なら M7・K6・T6・E3） | **`levels` は変えない**（企画 2.4「戻って遊んでも進み具合は進まない／戻らない」）。カード・統計は進む |

- 関門の記録（`cleared`）はどの場合でも、関門レベルで 4/4 なら付ける（すでにあれば日付を変えない）。記録はするだけで、解放を決めるのは 3.4。
- 「固定」（`locked[g]`）は今と同じく `nextLevel` を止める。
- **保護者がレベルを選んだとき**（保護者画面の「レベル」のドロップダウン、`src/ui.js:627`）: 選んだレベル L のステージに `stage.current` を揃える（`stage.current = stageOf(L)`）。揃えないと、たとえば S1 を選んでいる子に保護者が M5 を選んでも、上の表の「`lv` が s より下」に当たって M8 が出てしまい、保護者画面の表示と出題が食い違う。捨てた案: 固定（`locked`）のときだけ `playLevel` が `lv` をそのまま返す — 固定していないと同じ食い違いが残る。
- 保護者画面のドロップダウンは**解放済みのステージの範囲のレベルだけ**を出す（今は `P.LEVELS[g]` を全部出している。`src/ui.js:512`）。未解放のレベルを選ばせたいときは、先にステージを「ひらく」（3.6）。
- 下のステージへ自動で落とさない理由: S1 の入口（M8）で 0〜1/4 が続く子を S0 に戻すかどうかは、保護者が判断する方がよい（ステージ選択で S0 を選べる。保護者画面でレベルを選べる）。自動で落とすと「しょうぼうし なのに みならい の問題」になり、階級の見せ方（企画 2.5）と食い違う。

関数（`src/ladder.js` を新規。純粋関数。`problems.js` の後に読む）:

| 名前 | 形 | 内容 |
|---|---|---|
| `stageOf(levelId)` | → `'S0'`… / `null` | |
| `stageRange(stageId, game)` | → レベル ID の配列 | えいごの読み替えを含む |
| `gateOf(stageId)` | → `{ math:'M7', letter:'K6', clock:'T6' }` / `null` | 3.1 の導き方 |
| `playLevel(profile, game)` | → `{ level, review }` | 3.3 の表の「出題するレベル」と、復習かどうか |

`problems.nextLevel` は 5 番目の引数 `range`（レベル ID の配列）を省略可で足す。省略時は今と同じく `LEVELS[game]` 全体（既存テストはそのまま通る）。`ladder.afterSession` からは `stageRange(s, g)` を渡す。

### 3.4 関門の判定と昇格

### 3.7 ふりがなの方式（S1 以降の画面の文字。U4）

方針: **文言は 1 つの書き方で持ち、表示するときにステージに合わせて変える**。

- 文言の書き方: `'{出|しゅつ}{動|どう}'` のように、漢字と読みを `{漢字|よみ}` で書く。読みが無い部分はひらがなのまま。
- 変換（純粋関数 `furigana(markup, allowed)`）: `allowed`（使ってよい漢字の集合）に入っている漢字は `{ t: '出', r: 'しゅつ' }`、入っていない漢字は読みのひらがな `{ t: 'しゅつ' }` に置き換えた区切りの配列を返す。
  - S0 は `allowed` が空 → **全部ひらがなになる**（S0 のルールが仕組みで守られる）。
  - S1 は K8 の教材の漢字、S2 は K8 + K9 の漢字（`data.KANJI.S1` / `S2`。「教材で出した漢字だけ」U4）。
- 表示:
  - DOM の文字（ボタン・見出し）: `<ruby>出<rt>しゅつ</rt></ruby>` を作る関数 `rubyHtml(segments)`（ui.js）。`textContent` で入れられないので、文言は固定の表だけを使い、子どもの名前など外から来る文字は通さない（HTML を組み立てる箇所を限定する）。
  - Canvas の文字（現場の文言・カード）: 新規の `drawRuby(ctx, segments, x, y, size)`（scenes.js）。ふりがなは本文の 45% の大きさで上に。
- **読み上げには漢字を渡さない**: 読み上げは今どおり別に持つ文（`docs/design.md:25` の方針。「はしご車」を「くるま」と読む誤読があった）。ふりがなの文言から読み上げ文を作らない。
- 範囲を切る: 漢字を使ってよいのは **S1 以降を選んでいるときの子ども向け画面**（出動えらび・現場・ごほうび・昇格）だけ。タイトル・「だれが あそぶ？」・しゃこはステージに関係なく見る画面なので、R2 では S0 と同じ（ひらがな）にする。保護者画面は今の書き方のまま。
- テスト: `furigana(x, 空)` の結果にひらがな・カタカナ・記号以外が無い（全文言の表で検査）。`furigana(x, S1)` の漢字はすべて `KANJI.S1` に入っていて、すべてに読みが付いている。文言の表のすべての `{漢字|よみ}` の読みがひらがなだけ。

- **`gateOf` は次のステージの有無に関わらず「そのステージの各ゲームの最後のレベル」を返す**（レベルの無いゲームは含めない）。次のステージが無いうちは、`cleared` に日付が付くだけで何も開かない（S1 の関門は今 `{ math: 'M10' }`。K8・T7 が入ると 3 つになる。S2 を足す PR（R3）は、K8・T7 が入った後に行うこと。さもないと M10 だけで S2 が開く）。`cleared` に残せるキーは、全ステージの関門レベル（M7・K6・T6・M10）。
- **保存の補正を一つ足した**: `normalizeProfile` は、未解放のステージのレベルが `levels[game]` に入っていたら、解放済みの一番上のレベルに丸める（手で書き換えたデータ・再ロックの取りこぼしの保険。たとえば `unlocked: 'S0'` で `levels.math: 'M9'` → `M7`）。
- **保護者がレベルを選んだとき（3.3）の精密化**: `stage.current = stageOf(L)` を無条件にはしない。**いまのステージの範囲に L が無いときだけ**揃える（`ladder.chooseLevel`）。S1 を選んでいる子に もじ の K3 を選んでも `current` は S1 のまま（もじ は S0 の範囲で遊ぶので食い違わない）。無条件にすると、えいご のレベルを変えただけで かず が S0 の復習に切り替わってしまう。
- **昇格の画面（`s-promote`）**: ごほうびの「しゃこへ」「もういちど」のどちらを押しても、昇格があれば先に出す。そのあとの行き先は「すすむ」「あとで」どちらもタイトル（3.6 のとおり）。しゃこの上部のワッペンの並びは未実装（R2-b の範囲外。後続）。
- **ステージの札**は短い名前（`STAGES[].short`: みならい・しょうぼうし）で出す（iPhone 縦 390px で 2 つ並べるため。`rank` は昇格の文言に使う）。
- **M8**（`kind: 'mix'`）: 1 回 4 問のうち、11〜20 を数える問題が 2 問、くり上がりなしのたしざん（a 11〜18、b 1〜9−一の位）が 2 問。順番は無作為。10 より多いものは「10 個入りの箱 + ばら」で描く（`scenes.boxLayout`。数えるときの順は箱の中 → ばら。`items` の形は変えていない）。たしざんは「箱 + ばら ＋ ばら」を、横に並べるか縦に積むか、大きく置ける方で描く。M10 の「いなくなる b 個」は、並びのうしろ（ばら → 箱の右下）から。
- **M9・M10 の選択肢**: M9 は 10〜20 の範囲（誤答は ±1・±2 を優先。3 など「10 を数え忘れ」の数は入らない）。M10 は 1〜10。答えボタンは、選択肢に 11 以上が混ざる問題では数字だけ（点は 10 まで）。
- **確認パネル・`#debug:play-math-M8` などは、そのレベルのステージを解放して選ぶ**（確認用。保存にも書かれる）。

## 7. R4: Google ログイン（比較と方針のみ。**外部サービスの作成・キー発行・公開は承認事項**）

### 7.1 前提（確かめた事実）

- `file://` では Google ログインは動かない。Firebase Authentication は `http` / `https` などのページでしか動かない（Firebase の FAQ とエラーの報告）。Google Identity Services も「承認済みの JavaScript 生成元」が要る。→ **ホスティング（公開された URL）が必須**。`file://` で開いたときは、ログインの項目を出さずに第1段階（R1）のまま動かす。
- `localhost` は Firebase Authentication の承認済みドメインに最初から入っている（開発時の確認はローカルサーバーで可能）。
- iPad/iPhone の Safari（16.1 以降）は第三者のストレージを遮断するので、Firebase の `signInWithRedirect` は、アプリと `authDomain` を同じオリジンにする等の対応が無いと動かない。**Firebase Hosting（`<プロジェクト>.web.app`）に置き、`authDomain` をアプリのドメインにする**のが公式の推奨の 1 つ。`signInWithPopup` を使う手もあるが、モバイルでは使い勝手が落ちる・ブロックされることがある（Firebase 公式）。
- GitHub Pages は、無料プランでは**公開リポジトリだけ**（このリポジトリは private）。private のまま使うには有料プラン（Pro）が要る（GitHub 公式）。

### 7.2 案の比較

| 観点 | **A. Firebase Auth + Firestore（推奨）** | B. Google ドライブの appData（GIS + Drive API） |
|---|---|---|
| 保存先 | 運営（このアプリのプロジェクト）の Firestore | 保護者自身の Google ドライブの「アプリ専用の隠しフォルダ」。他のアプリや保護者のドライブ画面からは見えない。アプリをドライブから外すと消える（Google 公式） |
| ログインの続き | Firebase Auth が端末内にログイン状態を保つので、**保護者が一度ログインすれば、子どもが遊ぶたびに裏で同期できる** | GIS のトークン方式は**ブラウザにリフレッシュトークンを持たない**。アクセストークンは短命で、切れたら「ボタンを押すなど利用者の操作から」取り直す（Google 公式）。→ 子どもが遊んでいる間に切れると同期できず、保護者が「つなぐ」を押し直す運用になる |
| 個人情報の説明 | 運営側に子どものニックネームと進み具合を預かる。保護者のメールアドレス・表示名は Firebase Authentication の利用者一覧に入り、プロジェクトの管理者がコンソールで見られる | 運営は子どものデータを持たない（説明しやすい）。必要なスコープは `drive.appdata`（Google の分類で非センシティブ） |
| 料金 | Spark プラン（無料）: 請求先の登録不要。Firestore は保存 1 GiB、読み取り 5 万／日、書き込み 2 万／日、削除 2 万／日、転送 10 GiB／月。超えても課金ではなく、その月はその機能が止まる。Google ログインは無料。Hosting は保存 10 GB、転送 10 GB／月（Firebase 公式） | Drive API の利用は無料。保存は保護者のドライブの容量（数 KB） |
| 想定の使用量 | 1 家族あたり 1 出動 1 書き込み、起動時 1 読み取り。家族で使う範囲では無料枠の 1% にも届かない | — |
| SDK の読み込み | 公式の CDN（`https://www.gstatic.com/firebasejs/<版>/firebase-app.js` など）は ES モジュール（`import`）。公式は npm + バンドラを強く勧めるが、CDN も手段として載っている | GIS は `https://accounts.google.com/gsi/client` を Google から読む。**自前で置くことは非対応**（Google 公式）。Drive は REST を `fetch` で呼べる（gapi は不要） |
| ホスティング | Firebase Hosting が素直（7.1 の Safari の件） | どこでも良い（GitHub Pages なら公開リポジトリが条件） |
| 作る量 | ログイン・同期・削除。オフラインは R1 の端末内保存が正なので、Firestore のオフライン機能は使わない | ログイン・手動の保存/読み込み・削除。トークン切れの扱いが増える |

**推奨: A**。決め手は「一度ログインすれば裏で同期できる」こと。B は保護者がそのつど「つなぐ」を押す運用になり、依頼の「次回以降引き続き」「別の端末で引き継ぎ」を自然に満たせない。また、iPad/iPhone の Safari では R1 の記録が 7 日ルールで消えうる（2.8）ので、**裏で自動的にクラウドへ写しておけること自体が記録を守る手段になる**（Firebase のログイン状態も同じルールで消えうるが、そのときは記録はクラウドに残っており、ログインし直せば戻る）。

B を選ぶべき場合: 「運営側に子どものデータを一切置かない」をログインの便利さより優先する場合（U9）。その場合は「保護者画面の『ドライブに ほぞん』『ドライブから よみこむ』を押したときだけ同期する」設計に変える。

### 7.3 ビルドなし方針との整合（SDK の読み込み方）

| 案 | 内容 | 判断 |
|---|---|---|
| **1. ログインを押したときだけ `import()` で gstatic から読む（推奨）** | 既存の classic script はそのまま。新しい `src/cloud.js`（classic）の中で、保護者がログインを押したとき（とログイン済みの起動時）に `import('https://www.gstatic.com/firebasejs/<固定の版>/firebase-app.js')` などを読み、`window.Manabi.cloud` に `signIn / signOut / pull / push / deleteAll` を出す。版は固定（自動で上がらない） | ログインしない家庭・`file://` では外部への通信が一切起きない（第1段階の原則を守る）。ビルド不要。外部 CDN を使うので**方針の例外（承認事項。企画 U11）** |
| 2. SDK のファイルをリポジトリに同梱 | gstatic の ES モジュールを `vendor/` に置き、`import()` で読む | 外部 CDN は不要になるが、更新を手で行う。Firebase は npm を勧めている。GIS（案 B）は同梱不可 |
| 3. ビルド工程を入れる | npm + バンドラ | 方針（ビルドなし）を崩す。採らない |

- 動的 `import()` は classic script の中からも使える（`type="module"` に書き換える必要はない）。
- 名前空間版（compat、`firebase-app-compat.js` を `<script>` で読む形）は、今回の調査では公式文書で現行の配布状況を確かめられなかった。使うなら着手時に確認する。

### 7.4 保存の形（Firestore）

- 文書: `families/{uid}`（uid は Firebase Authentication の利用者 ID）。中身は `{ profiles: [...], deleted: { <id>: 'YYYY-MM-DD' }, updatedAt }`。プロフィールの形は R1 の v2 と同じ（`device` は送らない）。
- セキュリティルール（下書き）: `families/{uid}` は `request.auth.uid == uid` の本人だけ読み書き可。他はすべて拒否。
- 送る時: 出動が終わって保存したとき（数秒まとめてから 1 回）、保護者画面でプロフィールを変えたとき。失敗しても遊びは止めない（企画 4.2）。次の保存のときにもう一度送る。
- 受け取る時: 起動時（ログイン済みなら）と、保護者画面を開いたとき。

### 7.5 端末内の記録の引き継ぎとマージの規則（企画 4.3。U13 で確認）

R4 で足す項目: プロフィールごとに `updatedAt`（名前・絵・固定・ステージの手動操作をした時刻）、`ladderAt`（`stage` を変えた時刻）、家族の `deleted`（消したプロフィールの id と日付。消したものが別の端末から戻ってくるのを防ぐ）。

純粋関数 `mergeProfiles(local, remote)`（テスト対象）:

| 項目 | 規則 |
|---|---|
| 対応づけ | **プロフィールの id** で。名前やアイコンでは対応づけない |
| `name`・`icon`・`locked` | `updatedAt` が新しい方 |
| `levels` | ゲームごとに**レベルが高い方** |
| `cards` | 車ごとに**★が多い方** |
| `stats` | 項目ごとに**大きい方**（足し算はしない＝二重に数えない） |
| `cleared`・`promoted` | 和集合。日付は早い方 |
| `stage` | `ladderAt` が新しい方（保護者の再ロックを、古い端末の記録で取り消さないため） |
| `seen` | 新しい方（`lastPlayed` で比べる） |
| 片方の `deleted` にある id | 両方から消す |
| マージ後に 5 人以上 | 自動で決めない。保護者画面で「どの こを のこす？」を選ばせる |

初めてログインしたとき（企画 4.3-1）:
1. クラウドが空 → この端末のプロフィールを一覧で示し、「この アカウントに ほぞんする？」で保護者が選ぶ（選ばなかった子は端末内だけ）。
2. クラウドにある → 同じ id は上の規則で自動マージ。違う id どうしは別の子として並べ、名前が同じ組があれば「おなじ こ ですか？」と聞く（はい → 片方の id に寄せてマージ）。迷うときは「この たんまつの きろく／アカウントの きろく」を選ばせる。
3. ログアウト時: 「この たんまつの きろくを けす？」（共有のタブレット向け。企画 4.3-3）。

テスト観点: 規則の各行、`deleted` の効き、元の 2 つを書き換えない、`mergeProfiles(a, a)` が `a` と同じ（同じものを何度マージしても変わらない）、`merge(a,b)` と `merge(b,a)` の結果が同じ（`updatedAt` が同じときの決め方を固定して）。
